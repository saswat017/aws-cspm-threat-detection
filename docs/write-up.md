# Write-up: runtime cloud security

## 1. The shared responsibility model
AWS secures the cloud itself: data centres, hardware, the hypervisor and the managed
service software. The customer secures what they put **in** the cloud: identities and
permissions, network rules, data protection settings, logging, and how resources are
configured. Almost every public cloud breach is on the customer side of that line: a public
bucket, an over-privileged user, a leaked key, SSH open to the internet. This project works
entirely on the customer side.

## 2. CSPM vs. threat detection
| | Cloud Security Posture Management (CSPM) | Threat detection |
|---|---|---|
| Question | "Is my configuration safe right now?" | "Is someone doing something bad right now?" |
| Input | Current state of resources (API describe calls) | Activity: CloudTrail events, flow logs |
| Output | Findings + posture score, drift between scans | Alerts with time, actor, source IP, MITRE technique |
| Here | `scanner/` (custom checks + Prowler), `scanner diff` | `detection/` rules + engine, EventBridge/CloudWatch |
| Blind spot | Misses short-lived changes between scans | Misses insecure settings that never change |

They complement each other: when `simulation` opens SSH to the internet, detection raises
DET-001 within seconds (who, from where), and the next scan shows SG-001 as a **new**
finding (what is exposed now), until the revert makes it **resolved**.

## 3. How this differs from pre-deployment IaC scanning
The earlier project scanned Terraform with Checkov in CI and blocked insecure pull requests.
That is prevention, but it only sees code. It cannot see:
- changes made by hand in the console or CLI (drift),
- changes made by an attacker with stolen credentials,
- settings that are not in the code at all (root MFA, account-level options),
- behaviour: logins, secret reads, mass deletions.

Runtime security looks at the live account. In this repo the target Terraform passes
Checkov, yet every attack scenario still succeeds at runtime, and only the scanner and the
detections notice. **Prevention before deploy, detection after.**

## 4. Limitations
- **Emulator:** the demo runs on moto; CloudTrail and flow-log records are generated by the
  simulator (see `docs/emulator.md`). On real AWS, delivery delays apply (CloudTrail to
  CloudWatch Logs typically takes minutes, so real MTTD is minutes, not seconds).
- **Single region** (us-east-1) and a single account.
- **Detection logic is rule-based**: thresholds and patterns can be evaded (slow brute
  force below the threshold) and can produce false positives (an admin legitimately
  attaching AdministratorAccess). The `new_value` rule needs a learning period.
- **Metric-filter alarms** on real AWS count events account-wide; per-source grouping is
  only in the Python engine.
- **No auto-remediation** by design: the system assesses, detects, alerts and reports;
  a human decides and acts.
- **Read-only scanner**, but it needs broad read permissions (`SecurityAudit`); denied calls
  show as ERROR and lower the coverage figure instead of counting as a pass.
